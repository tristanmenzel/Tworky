# Tworky

A Tauri 2 desktop app for day-to-day work, for Windows, macOS and Linux (see Platforms). It shows a work list I curate: GitHub issues (shown with their epic › story parents and their subtasks), pull requests and custom work. **Begin session** on an issue creates an isolated *worker* and opens Claude in it, with no initial prompt. A worker starts as a port slot plus a folder holding a generated CLAUDE.md. You then tell Claude what to set up, using the `tw` CLI, which is on the session's PATH and reads `TW_WORKER_ID`:

- `tw worktree add <repo> [--branch b] [--base ref]` creates a git worktree (new, existing local or remote branch, or an adopted plain-git worktree) and renders that repo's config with the worker's ports
- `tw worker setup` starts the worker's own docker compose stack and runs setup hooks
- `tw service start <name>` starts one of the project's services (a dev server, say) on the worker's ports. Opening a browser tab starts the service its page needs

**Clean up** tears all of this down once the PRs are merged.

Everything on the list is an **item** with a random name such as `brisk-otter`, added from the **+** menu beside refresh: **From issue** (a search, defaulting to my open assigned issues), **From pull request** (my review requests, or any PR URL) or **Custom** (a title and description). Each belongs to a project, found from its repo. For a repo no project covers, the user adds it to an existing project or starts a new one. A new project is finished by a **project setup session**: Claude in a Setup tab under Projects, which configures it and tests it on a scratch item. Items stay on the list until removed, which they can't be while they have a worker.

## Layout

- `crates/core` (`tworky-core`) holds all domain logic and has no Tauri dependency.
  - `config`: app and project TOML.
  - `github`: `gh api graphql` / `gh pr list`. Auth is whatever `gh` is logged in as.
  - `hierarchy`: issue index and tree.
  - `worker`: plan, prepare, add/remove worktree, setup, launch, PR summary and cleanup.
  - Helpers: `git`, `ports`, `template` (minijinja, strict undefined), `stack` (docker compose), `accounts` (per-project test accounts), `services` (dev servers started on demand), `state` (SQLite).
- `crates/browser` (`tworky-browser`) automates a browser tab over the Chrome DevTools Protocol through a `Cdp` trait, so it doesn't depend on the host: accessibility snapshots, input, login detection and filling, mobile emulation and cookies. `PageEvents` is the host's feed of loads, URL changes and login messages, which the tools wait on. Tests use `FakeCdp`.
- `crates/cli` (`tw`) gives headless access to the same operations: `tw issues`, `tw worker create|ls|show|setup|stop|prs|jobs|stop-job|rm`, `tw worktree add|ls|rm`, `tw service ls|start|stop`, `tw memory show|add|path`, `tw subtask add`, `tw item ls|search|reviews|new|add-issue|add-pr|begin|link|rm`, `tw project ls|show|check|add-repo|done`, `tw cards`, `tw accounts ls|add|rm|set-password`, `tw session-state`, `tw issue bug|friction|comment`, `tw paths`.
- `src-tauri` wraps core in Tauri commands. `pty.rs` runs `claude` in a pty (`portable-pty`: ConPTY on Windows) and streams output over a `Channel<String>` with a 512 KB scrollback replay. `browser/` hosts the browser tabs (`webview2.rs` on Windows, `unsupported.rs` elsewhere for now) and the browser MCP server (`mcp.rs`).
- `ui` is a Svelte 5 + TypeScript + Vite frontend with three top-level views in `App.svelte`:
  - **Work Items**: `CardList` (issue cards, then PR and custom items) on the left, added through `AddIssueDialog`, `AddPullRequestDialog` and `NewItemDialog` (custom), with `ProjectChoice` when the repo is unknown. On the right, an Overview tab (`CardDetail` or `ItemDetail`) and a terminal tab for each worker on the selected work item. The Overview's left column holds the issue card (parents as breadcrumbs that expand in place, status pills, description, subtasks) above `LocalWork` (the workers' worktrees, services, jobs and stack). The right column holds `PullRequests` (branches and PRs). Under 1100px of pane width it's one column.
  - **Workers**: every worker, including ones no card covers any more, so each can be cleaned up. Each shows its `LocalWork`. **Go to work item** jumps to its card. Terminals of workers with no work item open here.
  - **Projects**: the configured projects, with Overview (`ProjectDetail`), Setup (the project setup session's terminal), Memory (`MemoryView`) and Accounts tabs. **+** makes a project from repos (`NewProjectDialog`) and opens its Setup tab.
  `LocalWork`, `PullRequests`, `StatusSelect` and `Markdown` are shared. Their **Ask Claude** buttons (prompts in `prs.ts`) paste a one-line prompt, stripped of control characters, into the worker's terminal (`terminals.ts`) without submitting it. They're disabled while the session isn't running or is waiting. Terminals stay mounted across views and selections, so switching away never drops a session's screen. A terminal tab has a `WorkerToolbar` (terminate or resume, open folder, clean up). `Terminal.svelte` uses xterm.js, which pastes only text, so an image-only paste sends Claude Code's image-paste key (Alt+V on Windows, Ctrl+V elsewhere) and Claude reads the OS clipboard itself.
- `examples/acme` holds the config for a fictional web app and API, the multi-service worked example in the project setup prompt.
- `examples/tworky` holds the config and memory seed for working on Tworky itself in Tworky workers (see Dog-fooding).

## Commands

- `cargo test --workspace`
- `cargo clippy --workspace --all-targets -- -D warnings` must pass. Run `cargo fmt --all` before committing.
- `npm run check` runs svelte-check. `npm run build` builds the UI.
- `node scripts/notices.mjs` regenerates `THIRD-PARTY-NOTICES.txt`. Run it after any dependency change; CI fails if the file is stale.
  - It needs `cargo install cargo-about --locked --version 0.9.3 --features cli`.
  - A devDependency whose code Vite bundles into `dist` must be added to `bundledDevDependencies` in the script, or it is left out.
  - The notices don't cover the system libraries the Linux AppImage bundles (webkit2gtk, GTK, libsoup). This is a known gap.
- `npm run tauri dev` runs the app. On Windows, `npm run dev:app` runs it inside a kill-on-close job object (`scripts/dev.ps1`), so Vite and the app stop when the launcher is killed, rather than leaving Vite on port 1420. Both launchers go through `scripts/tauri-dev.mjs` (`npm run dev:tauri` on Unix), which points Vite and `devUrl` at `TW_PORT_VITE` (default 1420) and, inside a worker, gives the app its own identifier. `npm run tauri build` builds the installer for the current OS: NSIS on Windows, `.app` and `.dmg` on macOS, `.deb` and AppImage on Linux. Targets and resources live in `src-tauri/tauri.{windows,macos,linux}.conf.json`, which Tauri merges over `tauri.conf.json`.
  - The build bundles a release `tw` (plus a `wa.exe` copy on Windows, see Rename transition), because sessions get the CLI on PATH from the app's install. `scripts/build-cli.mjs` builds it.
  - `tauri-build` checks that those resource files exist even for debug builds, so on a fresh clone run `node scripts/build-cli.mjs` before `cargo build` or `npm run tauri dev`.
  - On Linux, building needs `libwebkit2gtk-4.1-dev libayatana-appindicator3-dev librsvg2-dev libdbus-1-dev pkg-config`.
- `.github/workflows/ci.yml` runs fmt, clippy, tests and svelte-check on Windows, macOS and Ubuntu for pushes to main and for PRs. It builds no installers.
- `.github/workflows/release.yml` publishes a release, `build-<sha7>`, for every push to main: the NSIS installer, a universal macOS `.app` (as `Tworky-universal.app.tar.gz`) and an x64 AppImage. It keeps the newest 10. See Versioning and updates.
- Installing for users:
  - macOS / Linux: `curl -fsSL https://raw.githubusercontent.com/tristanmenzel/Tworky/main/scripts/install.sh | sh`
  - Windows: ``& ([scriptblock]::Create((irm https://raw.githubusercontent.com/tristanmenzel/Tworky/main/scripts/install.ps1)))``
- `cargo run -p tw -- issues` is the quickest way to check GitHub access and project routing.

## Commits

A commit a user would notice carries a `Change: <one terse line>` trailer, worded for users ("Cards show their board status"). Internal changes (refactors, tests, CI, docs) get none. Release notes are built from these.

## Runtime locations

`<config>` is `%APPDATA%\Tworky` on Windows, `~/Library/Application Support/Tworky` on macOS and `~/.config/Tworky` on Linux. `<data>` is `%LOCALAPPDATA%\Tworky\data`, `~/Library/Application Support/Tworky/data` and `~/.local/share/Tworky/data` respectively (`tw paths` prints both).

- Config: `<config>/config.toml` (optional; see `AppConfig` for keys) and `<config>/projects/*.toml`.
- Templates: `<config>/templates/<project>/`. This mirrors the worker layout (`<repo>/<path>`) and **holds secrets**, so keep it out of git.
- Settings the app writes: `<config>/settings.toml` (`keep_awake`). Parsed leniently, so a bad or unknown key falls back to its default.
- State: `<data>/state.db`.
- Shared memory: `<config>/memory/<project>.md`.
- Project setup sessions: `<data>/project-setup/<project>/`, holding the CLAUDE.md generated from `crates/core/src/project_setup.md`.
- Workers: `<workers_root>/<project>/<issue>-<slug>/<repo>`, `<workers_root>/<project>/pr<number>-<slug>/<repo>` for a pull request, or `<workers_root>/<project>/<item name>/<repo>` for a custom item. The default root is `C:\work` on Windows and `~/work` elsewhere.
- Source roots: `source_roots` in `config.toml` (default `C:\Source` on Windows, `~/Source` elsewhere). They're searched up to 3 levels deep for clones when picking repositories for an item. Repos that aren't cloned yet go to `<first root>/<owner>/<repo>`.
- `TWORKY_HOME` moves config and data under a single directory (`WORK_APP_HOME` still works).
- **Debug builds** (`npm run tauri dev`) with no `TWORKY_HOME` use `<local data>/Tworky-dev`, so in-progress code never rewrites config the installed app reads. The first run copies only the installed `config.toml`, pointing `workers_root` at a `-dev` sibling (`C:\work-dev`). It starts with no projects, templates, memory or state, because a dev build can't see the installed app's workers and would otherwise hand out their port slots and compose project names. Sessions inherit `TWORKY_HOME`, so their `tw` uses the same home. The OS credential store is still shared.
- **Dog-fooding.** A debug build started inside a Tworky worker (`TW_WORKER_ID` set, no `TWORKY_HOME`) uses `Tworky-dev/workers/<worker id>` and `<workers root>-dev/<worker id>` instead, and `tauri-dev.mjs` gives it identifier `com.tristanmenzel.tworky.dev.<worker id>` and the worker's Vite port (passed to Vite as `TWORKY_VITE_PORT`, so a plain `tauri dev` keeps 1420 and its `devUrl` in step), so several dev instances run side by side. Every build drops inherited `TW_*`, `WA_*` and `COMPOSE_PROJECT_NAME` at start, so the outer worker's values never reach the dev app's own sessions, hooks and services. With `examples/tworky/tworky.toml` installed as a project, `tw service start app` starts one. Known limits: cleaning up the worker doesn't remove its dev home or dev workers folder, nor stop stacks or services that the dev app's own workers started (they live outside the worker folder); and a dev build started from a worker of a *dev* Tworky inherits that instance's `TWORKY_HOME`, so it shares its home.

## Invariants

- **Ports.** A worker on slot N gets `base + N × port_stride`. Slot 0 is the main checkout. The allocator also rejects any slot whose ports clash with another service's shifted port.
- **Template output** should land on gitignored files. If a rendered file is tracked, provisioning marks it `skip-worktree` so per-worker values can't be committed.
- **Branches.** Cleanup deletes only branches Tworky created: those it branched from base (`new`) or made to track a remote branch (`tracking`). It keeps `existing` ones.
- **Setup and cleanup** are idempotent and resumable. A cleanup that fails partway keeps the worker record as `failed` so it can be retried. `git worktree remove` can stop partway when a file is held open, after it has deleted `.git`, so `git::worktree_remove` deletes whatever is left directly.
- **Terminate and cleanup stop what a session started.** Dev servers and test runs outlive `claude` and hold worktree files open. `process::stop_processes` stops `claude`'s process tree (pid taken before it is killed) plus anything whose command line, exe or working directory is inside the worker folder, never the caller or its ancestors. Windows lists processes through CIM and stops them with `taskkill /T`. Unix uses `ps`, reads working directories from `/proc` (Linux) or `lsof` (macOS), and sends SIGTERM to each tree, children first, then SIGKILL after 3s. Terminate then runs `docker compose stop`, which keeps the containers and volumes, so `tw worker setup` brings them back. Terminate, Stop stack and cleanup act on the configured `[stack]`, or on the compose project by name when its compose files are gone, so a Docker failure still leaves a cleanup `failed` for retry. Without a `[stack]` they act on the compose project only if `docker compose ps --all` lists containers, and skip it, with a log line, if `ps` fails. Terminate sets the record's `stopped` flag and setup clears it. While it's set, `launch` passes `--settings` with a `SessionStart` hook that tells Claude the stack and dev servers are down. It uses a hook rather than `--append-system-prompt` because a resumed conversation re-sends the system prompt it recorded on its first request. Closing the app stops each live session's `claude` tree and its jobs (`process::stop_sessions`), but not its stack and not other processes in the worker folder.
- **Jobs** (`process::jobs`, `tw worker jobs`, a ▶ tab per job, or one `▶ dev (N)` tab with a dropdown (`JobsMenu`) when there are two or more). A job is a process tree a session left running: a dev server, watcher or test run, at least 10s old. Its processes are under a shell that Claude's Bash tool started (found by `shell-snapshots` and `eval '<command>'` in its command line) or its PowerShell tool started (`CLAUDE_CODE_SHELL_LAUNCHER_SCRIPT` in the command line of a `cmd /c` launcher and the `pwsh` under it), or were started from inside the worker folder. The session's other children, such as MCP servers, are not jobs. The session's `claude` is found by its session id in the command line, so the CLI sees the same jobs as the app. Each job is reported from its outermost launcher (`npm run`, `sh -c`, `cmd /c`), and Stop kills from there. Git Bash on Windows loses parent links through its helper processes, so a detached tree that started within 5s of a Claude shell, and whose command appears in that shell's command, is merged into it. Output comes from Claude Code's undocumented task files: the transcripts in `~/.claude/projects/<session folder>/` map each background command to its `%TEMP%/claude/.../tasks/<id>.output`. A PowerShell-tool job, foreground or background, reads the `.output` file its root launcher redirects to (`> "<path>"`), and is labelled with the transcript's command for that file, else its first non-launcher process, else `PowerShell command`. Transcripts are read incrementally, and `read_output` only opens `.output` files under that temp folder. The app polls every 10s while its window is visible, because each Windows snapshot costs about 0.7s.
- **Session activity** (`activity.rs`, `WorkerDot`). Each launch's `--settings` adds hooks that run `tw session-state working|idle|waiting || true` (the `|| true` because a PreToolUse hook exiting 2 would block the tool). The states are: working on UserPromptSubmit (`--new-turn`, which also ends a handover and account requests) and PostToolUse; waiting on PermissionRequest, on PreToolUse for AskUserQuestion and ExitPlanMode, and on permission or elicitation Notifications; idle on Stop and SessionStart. SessionStart for `/clear` passes `--new-conversation`, which, like the app's New conversation, also ends a handover and account requests. The state is written atomically to `<data>/sessions/<worker>.json`. No hook fires when a prompt is answered, so typing into a waiting session marks it working. Esc ends a turn without a Stop hook, so a working session whose terminal has been silent for 20s (Claude's spinner repaints while it works) is marked idle. `watch_activity` polls the folder every 750ms, emits `session-activity`, and flashes the taskbar when the window is unfocused: urgently for waiting and once on entering `account`, gently for working → idle and for a handover.
- **Keep awake** (`keep_awake.rs`, `title.rs`, `power/`, `settings.rs`). The host is kept from idle-sleeping while a session's Claude is working. The signal is Claude Code's terminal-title spinner: the pty reader parses OSC 0 and 2 titles (`title.rs`, across reads, aborting an OSC on ESC without `\`, CAN, SUB or past 4 KB), and a title whose leading glyph differs from the previous title's and isn't `✳` is a tick. A live session is busy for 5s after its last tick, so the signal ends by itself after Esc, a crash or a change to the glyphs: it fails towards sleep. The controller thread (started in `setup` beside `watch_activity`) ticks every second, and at once when the mode changes. It leaves out a *stuck* session, one whose run of ticks has lasted 15 min with no write to its activity file, until its ticks stop for 5s; it notes the `Instant` at which it sees a record's mtime change and never does arithmetic on the mtime. `power::should_hold` decides from the mode (`keep_awake` in `settings.toml`: `off`, `plugged_in` (default) or `always`), the busy count and the power source, which is read at most every 15s and only while the mode is `plugged_in` and a session is busy. The lock is a `power::SleepLock` (a `PowerRequestSystemRequired` request on Windows, an IOKit `PreventUserIdleSystemSleep` assertion on macOS, the desktop portal's suspend inhibit under GNOME or KDE else a logind `sleep` lock on Linux), held while the rule says so and refreshed every tick. Lock and power failures are only logged, and a failed lock is retried at most once a minute; nothing reports them to the user. The `keep-awake-changed` event and `keep_awake_status` carry the mode, whether it holds, the busy count, whether it's on battery (when read), whether there's a battery and the lock kind; `set_keep_awake` writes `settings.toml`.
- **Services** (`services.rs`, `tw service`, `[[services]]`). A project's long-running processes: name, `cwd`, `run` (a hook command, rendered with the worker's ports), an optional `port` name, `https`, `needs` and `ready_timeout_secs`. A service with a port has the URL `<http|https>://localhost:<worker port>/` (`services::service_url`), which `tw service ls`, MCP `list_services` and the UI show, with its state: running (its port answers), starting (its process is alive but its port doesn't answer yet) or stopped. Each runs detached through `AppConfig.shell` with the worker's environment, its output in `<data>/services/<worker>/<name>.log`, and its pid, command and start token in `<data>/services/<worker>.json`. The start token is the OS's own record of when the process started, read from the child as it's spawned (`process::start_tokens`: the `GetProcessTimes` creation time on Windows, `/proc/<pid>/stat` start ticks since boot on Linux, `ps -o lstart` in UTC on macOS), so clock steps and DST don't change it. A recorded pid is the service while it runs with the same token; a different one means the pid was reused. Records made before tokens instead require the process to have started no later than the record's wall-clock start. Status, start and Stop all use this check, and reading tokens spawns nothing on Windows or Linux. It doesn't compare command lines, because on Unix the shell execs the command, so `PORT=1 npm run dev` runs as `node .../npm run dev`. A pid whose token can't be read counts as the service, but Stop then also requires its command line to contain the command, ignoring quotes and backslashes because Windows shows a quoted `"` as `\"`; if the lookup fails outright, status falls back to whether the pid exists. Starting one starts what it needs first, skipping any whose worker port already accepts connections (IPv4 or IPv6 localhost), so a server Claude started by hand counts, or whose recorded pid is still the service. It waits for a dependency to listen before starting what needs it, but only when something after it still has to start, then for the service itself, each within its `ready_timeout_secs` of its own start (`tw service start --no-wait` skips the waits). Stopping one that already died fails, and forgets it. On Windows, starting one first clears the inherit flag on `tw`'s own standard handles: Windows hands a child every inheritable handle, so the service would otherwise hold `tw`'s stdout pipe open and `tw service start | cat` would never return. A service is a job like any other, and its job tab tails that log. Opening a browser tab (the UI or `open_tab`) starts the service whose port the URL is on and waits for it, showing progress and any failure, with the log's tail, under the tab's address bar. A tab restored at startup, or one whose service failed to start, doesn't load a page whose service isn't listening. It's lowered under a panel with **Start <service>** and **Retry**, where Retry loads the page once the port answers, however the server was started. `worker_local` (`local.rs`) reports a worker's worktrees (checked-out branch, and `git --no-optional-locks status`, so polling never takes the index lock), services, stack containers (`docker compose ps`, 5s timeout), and listeners. A listener is whatever listens on a worker port that no service owns and no container publishes, read from the TCP table (`GetExtendedTcpTable` on Windows, `lsof` on macOS, `ss` on Linux) and shown read-only in LocalWork and MCP `list_services`. When `docker compose ps` fails, Docker's port holders (`com.docker.backend`, `wslrelay`, `vpnkit`, `docker-proxy`) count as the stack's. With no `[[services]]`, `list_services` and `tw worker setup` tell Claude to ask the user to add them in the project setup session, and `tw project check` warns when there are `[ports]` but no `[[services]]`, more softly when there's a `[stack]` that may publish them all. The `stop_service` and `stop_stack` commands stop one service or the stack (`docker compose stop`) and emit `worker-changed`. Terminate and cleanup stop the worker's processes and then each recorded service (on Windows a service's command line needn't mention the worker folder), and closing the app stops every service it knows of.
- **Accounts** (`accounts.rs`, `tw accounts`, Projects › Accounts). A project's `[[accounts]]` are test personas: name, username, a start page (exactly one of `start_url` and `start_service`), optional login origins, mobile and colour. A login origin may be `service:<name>`. Names are unique ignoring case. Passwords live in the OS credential store under service `tworky`, user `<project>/<account>`, never in the TOML. Edits go through `toml_edit`, so comments survive, and are written atomically only if the result still parses. A worker's accounts have their start URLs and login origins rendered with its ports, and services resolved to its service URLs and origins (`Workspace::worker_accounts`). An account naming a missing or portless service is left out with a warning rather than failing the list, and `tw project check` reports it. `login_origin_to_save` stores an origin seen on a worker as `service:<name>` for a service's port, `localhost:<base port>` for another worker port, else literally.
- **Browser tabs** (`src-tauri/src/browser`, `BrowserTab.svelte`). Opening an account on a worker makes a 🌐 tab beside its terminal. On Windows each is a wry child WebView2 of the main window with its own profile per worker and account (`profile_name`), in a data folder separate from Tauri's (`<data>/browser/webview`). WebView2 must be called on the main thread, so views live in a `thread_local` and calls go through `run_on_main_thread`. A native child paints over the DOM, so hiding a tab lowers it beneath the Tauri webview (`HWND_BOTTOM`) rather than hiding it: a hidden WebView2 doesn't load, and screenshotting it hangs. Show calls can arrive out of order, so each `browser_show` carries the UI load's random id and a sequence number: the host ignores one older than a show it already applied from the same load, and raises a view created after it was asked to. The UI lowers every tab while a dialog or overlay is up. Errors show in a bar above the panes, which shrinks the browser pane rather than covering it. A tab held back for a stopped service (see Services) loads on MCP `navigate` or `reload`, or from the address bar, once its page's port answers; until then the call fails and the tab stays paused on that URL. CDP goes through `CallDevToolsProtocolMethod`. The login detector runs in an isolated world (`tworky`) and reports through a `Runtime.addBinding` binding. Popups open as more tabs of the same account and profile. **Open browser › Anonymous** opens a tab with no account on one of the project's services (a picker when there are several), on a fresh profile `ta-<worker>-<tab id>-<random>`. It has no sign-in and no End session, isn't reopened after a restart, and closing its last tab deletes the profile, as cleanup does. **Create** (`CreateProfileDialog`) saves an account with username = the email and a `start_service`, then opens it. While an account has no login origins, a login page on an origin it doesn't allow offers **Fill <email>** (`browser_fill_email`), which fills the username and adds the origin to `login_origins` (asking first for a non-localhost origin). An allowed login form with a password field, for an account with no stored password, offers **Set password**, which stores it and fills the form, in place of **Sign in as**. `<data>/browser/state.json` (`browser/store.rs`) keeps the open tabs, the highest tab id handed out (`next_id`, so an anonymous tab's id isn't reused), and, per profile, its worker, kept cookies and whether it's anonymous. At start the saved tabs reopen with their ids, so handover buttons and Claude's tab ids survive a restart, at their last URL unless it was an OAuth redirect. Session cookies are given a 30-day expiry after each load and every minute, so sign-ins survive a restart, and **End session** deletes them. Cleanup closes the worker's tabs and deletes its profiles (`ClearBrowsingDataAll`, then `ICoreWebView2Profile8::Delete`, through a webview on that profile). Startup deletes the profiles of workers that no longer exist, which `tw worker rm` leaves behind, and every anonymous profile left over.
- **Browser MCP** (`browser/mcp.rs`). The app serves MCP over streamable HTTP on an ephemeral `127.0.0.1` port (Windows only, for now). Each launch gets `--mcp-config` naming server `TworkyWeb` with a fresh bearer token, held only in memory and mapped to the worker; relaunching or cleaning up revokes the old one. Nothing on disk registers the server, so Claudes started elsewhere never see it. Tools only reach that worker's tabs, including ones the user opened. The launch's settings allow `mcp__TworkyWeb`. `sign_in` fills credentials inside the page, so Claude never sees the password, and only on the account's own origins. `open_tab` without `account` opens an anonymous tab, which needs a `url`. The instructions tell Claude to `request_account` rather than work around a missing account.
- **UAT handover.** The `hand_over` tool stores a summary, steps and tab ids in the worker's session record. A session that is idle with a handover shows as `uat` (Ready for UAT): a blue dot and card pill, a topnav count and a gentle taskbar flash, ranked waiting > account > uat > idle. The work item's Overview shows it as a checklist with buttons for the tabs. It ends when the user sends Claude a prompt, presses Done or starts a new conversation. **Account requests** work the same way: the `request_account` tool (refused unless the project has a service with a port) adds a name, email, service and reason to the record's `account_requests`, replacing a pending one of the same name, and an idle session with any shows as `account` (Needs account), even with a handover. Typing doesn't change that state, and Ask Claude stays enabled. `AccountRequestPanel`, on the Overview and the terminal tab, has a **Create** per request that opens `CreateProfileDialog` prefilled; saving dismisses the request. Requests end on Dismiss or the next prompt. Testing guidance for Claude is in the MCP server's instructions, not the worker CLAUDE.md, so existing workers get it too.
- **Shared project memory** (`memory.rs`, `tw memory`, the Memory tab). Every launch passes a `SessionStart` hook that `cat`s the project's memory file, so a session gets the current version on start and on resume, not a copy frozen into CLAUDE.md. The worker CLAUDE.md tells Claude it is one of several parallel sessions, and that it should propose facts for the user to approve before running `tw memory add`. Writes take a lock on `<project>.md.lock` and replace the file atomically, so parallel workers don't lose entries.
- **Issue status** is the issue's state, not a Projects board field: Open, Done (closed as completed) or Not planned. Changing the close reason reopens the issue and closes it again, rather than relying on `closeIssue` to update an already-closed issue (`github::state_steps`).
- **Tworky issues** (`feedback.rs`, `tw issue`). Sessions are told, in the worker CLAUDE.md and an always-on `SessionStart` hook, to propose Tworky bugs and friction to the user and only then run `tw issue bug|friction "<title>" --body-file -`. It files on `AppConfig.tworky_repo` (default `tristanmenzel/Tworky`) with a `bug` or `friction` label. It lists similar open issues and exits non-zero unless `--force`, so Claude can use `tw issue comment <n>` instead. The appended footer carries only the `tw` version, OS and whether it's a dev build. Worker ids and project names stay out: an id holds the issue number and title slug, and either can name a private client. The label is created only when gh reports it missing, so its colour survives.
- **Graft.** Preparing or launching a worker writes `<worker>/.claude/graft-settings.json` with `plan.outsideRepoPlans = here` unless the file exists, so Graft's plan and execute treat the worker folder as a folder of repos and add them with `tw worktree add`. It relies on Graft reading project settings from `.claude/` (pleb/graft#29, already in the `my-graft` fork).
- **Claude sessions** get no initial prompt. They start with `--session-id <uuid> --permission-mode auto`. After that the session id is marked started, and later launches use `--resume <uuid>`. Project setup sessions are the exception (see below).
- **GitHub writes** (`TW_GITHUB_WRITES` and `GH_WRITES` in `worker.rs`). Auto mode's classifier blocks GitHub writes ("External System Writes") unless the user's own message names the exact action; an answer to Claude's question or a plan approval reaches Claude as a tool result, which the classifier never sees. Permission rules are checked before the classifier, so every launch's `--settings` (Bash and PowerShell) allows `tw subtask add` and `tw issue` outright, and has `permissions.ask` rules for `gh issue create|comment` and `gh pr comment|review`, which show the command in a permission prompt. The worker CLAUDE.md tells Claude to use those commands rather than `gh api`, which prefix rules can't tell apart from reads, and to run each write as its own command.
- **Project setup sessions** (`project_setup.rs`, the `project_sessions` table, `tw project`). One per project, run under the id `setup@<project>` (worker ids never contain `@`), so they share the pty, activity files and terminal code with workers. The cwd is the setup folder, with `--add-dir` for the projects folder, the project's templates and each repo. `TW_PROJECT` is set instead of `TW_WORKER_ID`, so `tw memory` and `tw accounts` default to the project, and the activity hooks pass `--worker setup@<project>`. A new conversation starts with a prompt (set up, or adjust) in the default permission mode, because the session has one job; later launches resume. Projects Tworky makes carry `onboarding = true` until the session runs `tw project done`. The session tests the config on a scratch item (`tw item new --scratch`), which is removed with its worker. `tw project check` tries a config on this machine: clones and their origins, templates and hooks rendered for slot 1, commands missing for an OS, services without a port. Stopping a setup session only kills its `claude`; there's no stack.
- **Session trust.** Before spawning, the session folder is marked `hasTrustDialogAccepted` in `~/.claude.json`, keyed by the path with forward slashes. The file is edited as raw JSON with `preserve_order`, so only that flag changes.
- **Session environment.** `pty.rs` removes the `NO_COLOR`, `FORCE_COLOR`, `CLAUDECODE` and `CLAUDE_CODE_*` variables the app inherited. Without that, a session started from a Claude-launched app has no colour and believes it is a nested child session. Replaying scrollback to a re-attached view strips terminal queries (`ESC[6n`, DA, OSC 10/11), because xterm.js would otherwise answer them again as typed input. The first attach keeps them: ConPTY asks for the cursor position before the program starts and waits for the answer, which only the view can give.
- **Cards** (`cards.rs`, `tw cards`). One card per issue item, whatever its state or assignees, with no roll-up. `github::issues_by_id` loads the listed issues with their ancestors and sub-issues. An issue GitHub no longer returns (deleted, transferred) gets a placeholder from the stored `IssueRef` (`state` `UNKNOWN`), so its card stays until removed. `no_rollup_into` is no longer used but still parses.
- **Subtasks.** A card's overview lists its sub-issues of the project's `subtask_types` (default Subtask, Sub-task and Task). A parent's other sub-issues are fetched only when the listed issue is itself a subtask; otherwise a listed story would pull in every story in its epic. Existing work for a subtask card is taken from its parent story.
- **Existing work** (`existing.rs`, `pulls.rs`, `tw work <issue-url>`). `existing_work` takes a `WorkSubject`: an issue, or an item (an issue item counts as its issue). It always includes the branches recorded for, or checked out in, the subject's workers' worktrees, limited to the subject's project. For a PR item it fetches the PR by number. For an issue it also collects branches and PRs for the issue and its sub-issues from three sources:
  - PRs that close, mention or are connected to any of them (timeline cross-references)
  - branches linked on GitHub
  - branches in the project repos whose names contain one of their numbers as a whole digit run
  Next-step signals come from `next_steps`, which is pure and unit-tested. A `BranchWork` with an open PR has a `verdict` (Needs attention, Draft, Ready, In review) from `existing::verdict`, which shares `is_ready` with `next_steps`. Failing checks carry links to their runs. Approvals are read from each reviewer's latest review, because `reviewDecision` is empty when a repo doesn't require reviews. The app fetches the project repos at most every 5 minutes, unless refreshed by hand. A branch without a PR has a ⋯ menu (``ActionMenu``) in `PullRequests` offering **Delete branch**, which removes origin and then local (``existing::delete_branch``). It refuses the base branch, a branch checked out in any worktree, and the head of an open PR, because deleting that would close the PR.
- **Board status.** Issues carry their Status on each open Projects board (`Issue::boards`). The project's `status_board` (a board number) picks which board the cards and dropdowns show. With it unset, or when the issue isn't on that board, every board is shown. Reading boards needs the `read:project` scope. Without it, `with_boards_if_allowed` retries the query without board fields, so issues still load. Editing needs `project` (`gh auth refresh -s project`).
- **Issue images** on private repos only load with GitHub auth. `Markdown` points GitHub-hosted `img` sources at the `ghimg` URI scheme. `main.rs` serves that scheme with `github::fetch_asset`, which runs curl with the `gh` token passed on stdin, and caches each image in memory. Only `github.com` and `*.githubusercontent.com` URLs get the token, and curl drops it on the redirect to the signed image host.
- **Items** (`items.rs`, the `items` table in `state.db`). An item's `source` is `custom`, `issue` (an `IssueRef`) or `pull_request` (a `PrRef` with head and base); rows from before sources existed read as `custom`. An issue or PR can be listed only once.
  - **Migration:** `State::open` runs schema version 1 once (the `meta` table): every issue a worker holds becomes an issue item, so the list starts with today's workers. Any build that opens a `state.db` migrates it, so test a debug `tw` with `TWORKY_HOME` set rather than against the installed app's state.
  - **Worker subject:** a worker has exactly one of `issue` or `item`. An issue item's worker is the issue's worker (`<project>-<number>`), found through the issue id. A PR item's worker has `item` and `pr`, id `<project>-pr<number>`, and its branch is the PR's head, so `tw worktree add` tracks it and cleanup never deletes it. A custom item's worker id is `<project>-<item name>`. Templates see an item as an `issue` whose `number` is the name, so issue branch templates still give unique branches.
  - **Lifecycle:** items stay until removed. Cleanup leaves the item, except a `scratch` one, and `remove_item` refuses while a worker exists.
  - **Searching** (`github::search_issues`, `tw item search`). Plain GitHub search spans all public repos, so text is searched with `in:title` and a `user:` qualifier for the viewer, their orgs and the owners projects name. A bare number is looked up (in parallel) in every known repo: those projects name or have clones of, and the repos of listed issues and workers. A URL or `owner/repo#n` is fetched directly. Each hit comes with up to four levels of parents (`matched: false`), so the dialog shows matches under their epic › story; parents with no match under them are dropped. For the default assigned search, a listed issue stays only as the parent of an unlisted match. `tw item search` prints matches only.
  - **Projects for new items:** an item goes in the project its repo matches. Otherwise the UI asks: `ProjectChoice::Existing` adds the repo to that project (`config::add_repo_to_project`, through `toml_edit`, so comments survive), and `New` makes a project for it.
  - **Linking:** `link_item` turns a custom item into an issue item. It only accepts an issue from the item's project, and refuses an issue that already has a worker or an item. It moves the worker to the issue (same id, folder, branch and stack) and rewrites its CLAUDE.md.
  - **Unconfigured repos:** picking them writes a minimal `projects/<name>.toml` (`match.repos` plus `[[repos]]` with the default branch as base, `onboarding = true`, and no ports, stack or hooks) for its setup session to finish. `config::create_repo_project` never overwrites a file.
- **Rename transition.** The app was called work-app, with a `wa` CLI, until the rename to Tworky. Workers made before then still have CLAUDE.md files, `.env` files and notes that use the old names. Until those are gone:
  - `worker_env` sets every `TW_*` variable together with a `WA_*` twin.
  - The CLI falls back to `WA_WORKER_ID`.
  - The installer ships `wa.exe` as a copy of `tw.exe`.
  - On first run, `Paths::migrate_legacy` copies `%APPDATA%\work-app` and `%LOCALAPPDATA%\work-app\state.db` to the new folders, and never overwrites anything already there.
  - Workers keep the `compose_project` saved on their record, so `wa-<id>` stacks still work alongside new `tw-<id>` ones.
- **Versioning and updates** (`build_info.rs`, `update.rs`, `VersionBadge`, `scripts/install.{sh,ps1}`).
  - **Build commit.** `crates/core/build.rs` embeds the build commit (`GITHUB_SHA` in CI, else `git rev-parse HEAD`) and a dirty flag. `tw --version` and the `tw issue` footer show it.
  - **Release notes.** `scripts/release-notes.sh` writes each release's body: a bullet per `Change:` trailer since the newest published release, then the `commit:` line `update.rs` reads.
  - **Badge.** The badge by the username compares the commit with the latest release through the unauthenticated GitHub API (`curl` on `…/compare/<commit>...<tag>`). A rate-limited request shows the status as unknown. `ahead_by` is how many commits behind this build is. A commit GitHub doesn't know, or no release at all, shows the short sha in grey. Dev builds show no badge.
  - **Unsigned releases.** They're safe to run because the install script downloads them with curl (`install.sh`) or `Invoke-WebRequest` (`install.ps1`). Neither sets Mark-of-the-Web (SmartScreen) or `com.apple.quarantine` (Gatekeeper). macOS bundles carry an ad-hoc signature (`signingIdentity: "-"`), which Apple Silicon needs to run them at all.
  - **Update.** **Update** fetches the current install script into `<data>/update/` and starts it detached (`process::spawn_detached`, which breaks out of `dev.ps1`'s job). The script runs while the app keeps working: `downloading`, then `ready` in `status.json`, with output in `update.log`. It then waits for the app's pid to exit.
  - **Restart to update.** This writes `<data>/update/relaunch` and exits the app, which stops sessions and services as on any close. The script installs (NSIS `/S`; replace `/Applications/Tworky.app`; or copy the AppImage to `~/.local/share/Tworky`), then reopens the app only if `relaunch` exists. Quitting normally while an update is `ready` installs it without reopening.
  - **Failures.** A failed download leaves the installed app alone. A failed install still reopens the old app. Either way `failed` stays in `status.json` for the badge to show.
  - **No `exit` in the PowerShell script.** It never calls `exit`, because run as the one-liner that would close the user's shell.
- **Child processes** go through `process::command`. On Windows it sets `CREATE_NO_WINDOW` so the GUI never flashes console windows.
- **Hooks** run through `AppConfig.shell`: `pwsh -NoProfile -NonInteractive -Command` on Windows, `bash -lc` elsewhere, so a login profile's PATH (nvm, Homebrew) applies. `run` is either one command for every OS or a table:
  ```toml
  [[hooks.setup]]
  cwd = "api"
  run.windows = "npm ci; if ($LASTEXITCODE) { exit $LASTEXITCODE }; npm run db:migrate"
  run.unix = "npm ci && npm run db:migrate"
  ```
  `macos` and `linux` keys beat `unix`. A hook with no command for the current OS fails setup rather than being skipped, so a worker is never left half set up.

## Platforms

Most of the app is portable: `portable-pty`, `gh`, `git`, `curl`, docker compose, the opener plugin, and the bash `SessionStart` hooks. What differs:

- **Process stopping** and **hook shells**: see the invariants above.
- **PATH on macOS.** An app started from Finder or the Dock gets launchd's bare PATH, so `claude`, `gh`, `docker` and `node` wouldn't be found. On Unix, when stdin isn't a terminal, `main` first runs `$SHELL -ilc` once (5s timeout) and takes that shell's PATH.
- **The bundled `tw`** sits next to the executable on Windows and in dev builds. In a macOS or Linux bundle it's in the resource folder. `with_cli_on_path` checks both.
- **Credentials** (account passwords) go through `keyring`: Credential Manager, the macOS Keychain, or Secret Service on Linux (GNOME Keyring or KWallet must be running). With no Secret Service, storing a password fails, every account shows as having no password, and deleting one is a no-op.
- **Unsigned builds.** Releases aren't signed or notarised. They install cleanly only through `scripts/install.*` (see Versioning and updates). A copy fetched by a browser or AirDrop needs `xattr -dr com.apple.quarantine Tworky.app` on macOS, or *More info › Run anyway* on Windows.
  - Windows Smart App Control, when it's on, blocks unsigned apps however they arrive.
  - On macOS the ad-hoc signature changes with every build, so the Keychain asks again after each update before Tworky can read stored account passwords.
- **Project TOMLs** hold absolute `source` paths, so each machine keeps its own copy. Write hooks with `run.windows` and `run.unix` when a config is shared between OSes.

macOS smoke test after `npm run tauri build`:
1. Open `target/release/bundle/macos/Tworky.app` from Finder, not a terminal, so the PATH import is exercised. Issues load.
2. Begin session opens Claude in a terminal tab, and `which tw` inside it points into `Tworky.app/Contents/Resources`.
3. `tw worktree add` and `tw worker setup` run the `unix` hooks and bring the stack up on shifted ports.
4. Start a dev server from the session, then Terminate. The dev server and the containers stop. Resume shows the stopped-stack note.
5. Clean up removes the worktrees, branches and folder.
6. Issue images load, and memory edits save.
